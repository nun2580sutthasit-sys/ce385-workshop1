1 — บัตรแนะนำตัว (`ex1-profile.js`)
ใช้ `const` ประกาศตัวแปรเก็บข้อมูล 5 อย่างตามเงื่อนไขเพื่อป้องกันการ Re-assign ค่า และใช้ Template Literal (Backticks `` ` ``) จัดรูปแบบการแสดงผลบัตรแนะนำตัว
คำนวณปีที่จะจบผ่านนิพจน์ `${2569 + remainingYears}` ภายใน Template Literal โดยไม่ใช้เครื่องหมาย `+` ในการต่อข้อความตามที่โจทย์กำหนด

2 — ชนิดข้อมูลและ typeof (`ex2-types.js`)
ตรวจสอบชนิดข้อมูล dynamic types ทั้ง 6 ชนิดผ่านคำสั่ง `typeof` แทรก `${typeof variable}` ในข้อความเพื่อหลีกเลี่ยงการพิมพ์ชื่อชนิดข้อมูลแบบ Hardcode
 
 อธิบายพฤติกรรม `typeof null` ที่คืนค่าเป็น `"object"` (ข้อจำกัดดั้งเดิมของ JavaScript) และ `typeof NaN` ที่คืนค่าเป็น `"number"`
ทดสอบ Type Conversion ด้วย `Number()` และปรับทศนิยมด้วย `.toFixed(1)`
เปรียบเทียบความแตกต่างระหว่าง Strict Equality (`===`) ของ String และ Number

3 — เครื่องคิดเลขคะแนน (`ex3-calculator.js`)
ดึงตัวเลขเกณฑ์คงที่ (60, 20, 100, 80) ออกมาตั้งเป็นตัวแปร `const` ชื่อตัวพิมพ์ใหญ่ (เช่น `WORKSHOP_FULL_RAW`) เพื่อป้องกัน Magic Numbers กลางสูตรคำนวณ
คำนวณคะแนนทุกขั้นตอนด้วยประเภทข้อมูล Number ใช้ `.toFixed(2)` แปลงเป็น String ทศนิยม 2 ตำแหน่งในขั้นตอนการแสดงผลด้วย `console.log` เท่านั้น

ข้อที่ 4 — ตัดเกรดจากคะแนน (`ex4-grade.js`)
สร้างฟังก์ชัน `toGrade(score)` ตรวจสอบข้อมูลนำเข้า (Validation) โดยเช็ก `< 0` หรือ `> 100` เป็นอันดับแรกเพื่อปฏิเสธข้อมูลที่ไม่ถูกต้อง
JavaScript ประมวลผลเงื่อนไข `if / else if` จากบนลงล่างทันทีที่พบเงื่อนไขที่เป็นจริง (True) เรียงจากน้อยไปมาก (เช่น เช็ก `>= 50` ก่อน) คะแนน 95 จะติดเงื่อนไข `>= 50` และได้เกรด D ทันที

5 — ระบบสั่งอาหาร (`ex5-food.js`)
ใช้ `switch-case` ในการหาเมนูและขนาด ใช้เทคนิค **Fall-through** รวม `case "ข้าวผัด"`, `"ข้าวมันไก่"`, `"ข้าวหมูแดง"`ลดโค้ดซ้ำซ้อน
ใส่ `default` ครบทุก `switch` รองรับข้อมูลไม่อยู่ในเงื่อนไข และสร้าง Array ของ Object เพื่อทดสอบคำนวณราคารวมทั้งบิล

6 — ระบบตรวจสอบสิทธิ์ (`ex6-auth.js`)
สร้างฟังก์ชัน `login()` ตรวจสอบเงื่อนไขตามลำดับความสำคัญ โดยใช้ `===`, `!==` และตัวดำเนินการตรรกศาสตร์ `||`
คำตอบท้ายข้อ
  1.ทำไมต้องตรวจ username/password ก่อน role: กระบวนการยืนยันตัวตน (Authentication) ต้องเกิดขึ้นก่อนการให้สิทธิ์ (Authorization) เสมอ
  2.หากย้ายการตรวจอายุขึ้นข้อแรก: จะเกิดปัญหาความปลอดภัยประเภท Information Leakage เนื่องจากผู้ไม่หวังดีสามารถสุ่มเช็กเงื่อนไขได้โดยที่ยังไม่ได้พิสูจน์ตัวตน
